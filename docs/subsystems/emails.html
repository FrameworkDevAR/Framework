Emails

Compose and send email through pluggable providers — with a queue for bulk delivery, localized content, a shared HTML template and a white list for safe testing.

Sending

Email::send() sends one message and returns an EmailResult. By default it wraps the message in the HTML template, honours the white list, and does nothing when email is disabled:

use Framework\Email\Email;
use Framework\Email\EmailResult;

$result = Email::send(
    toEmail: "user@example.com",
    subject: "Welcome",
    message: "Thanks for joining!",
);

if ($result === EmailResult::Sent) {
    // delivered
}

A few flags adjust that behaviour:

ArgumentEffect
sendAlwaysBypass the white-list filter for this send.
sendTestSend even when email is inactive — for a config test.
withoutTemplateSend the raw message without the HTML wrapper.

Send results

Rather than throw, a send returns an EmailResult — Sent on success, or the reason it did not go out, so callers can branch on it:

ResultMeaning
SentHanded off to the provider.
InactiveSendEmail is turned off (EMAIL_ACTIVE).
WhiteListFilterThe recipient is not on the white list.
InvalidEmailThe address is malformed.
NoEmailsNo recipients were given.
NoProviderNo EMAIL_PROVIDER is set, so there is nothing to send through.
ProviderErrorThe provider rejected the message.

Configuration

Email is configured entirely through environment values, which the build turns into typed Config getters. A few shared keys govern every send, whichever provider you use:

KeyControls
EMAIL_ACTIVEThe master switch — with it off, send() returns InactiveSend and nothing leaves.
EMAIL_PROVIDERWhich transport to send through (see below).
EMAIL_NAME / EMAIL_EMAILThe default "from" name and address on every message.
EMAIL_REPLY_TOThe default reply-to address.
EMAIL_USE_WHITE_LISTRestrict delivery to the white list.

Because these live in .env, each environment can use a different setup with no code changes — a real provider in production, and email switched off (or the white list on) locally:

Providers

EMAIL_PROVIDER names an EmailProvider — one of the transports below. When you call Email::send(), it builds the message from the shared "from" identity and hands it to the matching transport: the API providers post to their HTTP API, while SMTP sends over a plain mail server. If the transport rejects the message, the send returns ProviderError.

There is no transport to fall back on. A send with EMAIL_PROVIDER unset returns NoProvider and nothing is built, so a setup that was never finished says so rather than reaching for a mail server nobody named.

Each provider reads its own credentials, so switching is just a matter of changing EMAIL_PROVIDER and filling in that provider's keys.

Writing your own

The enum is not a list you edit. A transport is a class implementing EmailSender, and the build finds every one of them — in the framework and in your app — and writes the EmailProvider enum from their names. The class name is the case, so a Postmark class is EMAIL_PROVIDER = "Postmark".

Its keys are yours to name. Add them to the .env the way every other setting is added, and the build turns each one into a typed Config getter — an UPPER_SNAKE key becomes get plus its name in camel case:

The sender then reads them back with Config::getPostmarkKey() and Config::getPostmarkUrl(), and answers whether the message was taken:

When the class is not what you want the config to say, name it with a Name constant and that is the case instead:

class AmazonSes implements EmailSender {

    public const Name = "SES";   // EMAIL_PROVIDER = "SES"
}

Run ./framework build and the provider is there. Nothing else changes: the white list, the template and the queue all sit in front of the sender.

Sending in a test

A test wants the send to run the whole way — white list, template, the lot — and stop before anything leaves. Write a sender that keeps what it is handed, and give it to Email::setSender(). It is handed over rather than named in the config, since the build only writes the providers it finds in the source:

use Framework\Email\Email;

Email::setSender(TestEmailSender::class);
Email::send("someone@myapp.com", "Hello", "A message");

Email::setSender();   // back to the one of the config

It differs from EMAIL_ACTIVE = false, which stops the send before anything is built and answers InactiveSend.

The queue

For bulk or deferred delivery, push messages onto the EmailQueue instead of sending inline, so a slow provider never blocks a request:

use Framework\Email\EmailQueue;

EmailQueue::add($content, "user@example.com");   // enqueue a message
EmailQueue::sendAll();                           // send everything pending
EmailQueue::deleteOld();                         // prune rows past EMAIL_DELETE_DAYS

Run sendAll() and deleteOld() on a schedule from your server's cron. First expose each as a console command:

use Framework\Discovery\Attr\ConsoleCommand;
use Framework\Email\EmailQueue;

class EmailCommands {
    #[ConsoleCommand("sendEmails")]
    public static function send(): void {
        EmailQueue::sendAll();
    }

    #[ConsoleCommand("cleanEmails")]
    public static function clean(): void {
        EmailQueue::deleteOld();
    }
}

Then add the crontab entries — one to flush the queue often, one to prune daily:

# crontab
* * * * *   cd /srv/app && ./framework sendEmails
0 3 * * *   cd /srv/app && ./framework cleanEmails

White list

The white list is a safety net for non-production environments. Turn it on with EMAIL_USE_WHITE_LIST, and send() delivers only to addresses you have added to the EmailWhiteList — every other recipient is skipped with a WhiteListFilter result. Staging can then run the real send path with no risk of emailing real customers.

Manage the list with EmailWhiteList::add(), edit() and remove(), and pass sendAlways: true on a message that must always go out — a password reset, say — to skip the filter for that one send.

Emails as classes

An email can also be a class extending EmailMessage. Its own static send() takes the data as typed parameters, so PHPStan checks every send, and its texts are written in the class, the $subject and the $body with a text per language, so the whole email in every language reads in one file:

The texts are Mustache with the data, and {{site}} is the app name. The lines are trimmed, so they can be indented, and a language that is not in the class uses the root one. The $body is made of paragraphs, like the stored content. The send() of the email gives the recipient, the language and the data to queue(), which renders it and adds it to the queue with the class name without the suffix as its code, and with a dataID when one is given as its last argument. An email that can not wait for the queue sets public static bool $sendNow = true:

WelcomeEmail::send(
    email:    "john@example.com",
    language: "en",
    name:     "John",
);

An email that needs its own HTML names a .mu template in a public static ?Template $template. The template has no texts: the subject and the body of the language are rendered with the data and given to it next to the data, and the $body can be left out. It can use the partials of data/email, written with inline styles and tables, each one reading its own key and rendering nothing without it. An app replaces one by writing a file with the same name in its own data/email:

PartialReads
{{> Button}}button, with a url and a text.
{{> Quote}}quote, HTML in a grey bubble.
{{> Avatar}}avatar, a circle with the initials over a color.
{{> Footer}}footer, a small grey line.
{{< Card}}A bordered box around its {{$content}} block.

The build adds the code of every class to the EmailCode enum, and EmailCode::getMessages() returns the classes by their code. The PHPStan rules check that every Email has a $description, a $subject, a send() and a text for each language.

A migration writes the texts of every class into the email_content table too, one row per language, and the row of a class that is gone is removed. A class is written again on every migration, unless it sets a public static int $version, which is what lets its texts be edited in the table: the row is then only written again when the class has a higher version than the one the row holds, and queue() sends the texts of the row rather than the ones of the class. So an app raises the version of the row when it edits it, and the class raises its own when its texts change and they have to replace what was edited.

The stored content

The texts of each email class are kept in the email_content table, one row per code and language, which is what an admin screen lists, and what it edits when the class has a version. EmailContent::get() returns the row of a code in a language, or in the root one when it has none in that language, and it can be handed as it is to sendContent():

use Framework\Email\Email;
use Framework\Email\EmailContent;
use Framework\System\EmailCode;

$content = EmailContent::get(EmailCode::Welcome, "en");
Email::sendContent($content, "user@example.com");

An admin screen saves its changes with EmailContent::edit(), which takes the subject and the message and raises the version of the row, and does nothing to a row with no version, as its class is not one that can be edited. Mustache::getError() says whether the new texts render, and the public static array $variables of the class, where it describes each variable its send() gives, is what the screen shows beside the form.

The stored copy renders through Mustache, so EmailContent::render() fills the message's {{placeholders}} with per-send data, and EmailQueue::add() takes the very same content when you want it queued instead of sent inline.

The HTML template

Unless you pass withoutTemplate, every message is wrapped in one shared HTML template, so all mail carries the same branded shell. send() loads the file named by EMAIL_TEMPLATE, renders it with Mustache, and drops your message into it — you write only the body (plain text or HTML), and the template supplies the header, logo and footer around it.

You do not have to write one to start. The framework ships a working template at data/email.html — a centered, responsive shell with the logo above the message — and EMAIL_TEMPLATE points at it by default. The path is looked up in your app first and only then in the framework, so dropping your own data/email.html into the project replaces it without touching the configuration. Point EMAIL_TEMPLATE somewhere else to keep both.

The template is a normal HTML file with a handful of placeholders that send() fills in:

PlaceholderFilled with
{{message}}Your message — the body passed to send().
{{name}} / {{siteName}}The application name.
{{logo}} / {{logoHeight}}The logo file name (EMAIL_LOGO) and its height — the shipped template builds the src as {{files}}/{{logo}}.
{{url}}The email base url (EMAIL_URL).
{{files}}The app's files base url.
 
<!-- the EMAIL_TEMPLATE file -->
<table>
    <tr><td><img src="{{logo}}" height="{{logoHeight}}"></td></tr>
    <tr><td>{{{message}}}</td></tr>
    <tr><td>{{siteName}}</td></tr>
</table>

Note the triple braces around {{{message}}} — Mustache escapes with double braces, so a body that contains HTML is inserted raw with three. Its path and branding come from these keys:

KeySets
EMAIL_TEMPLATEPath to the HTML template file.
EMAIL_LOGO / EMAIL_LOGO_HEIGHTThe logo image and its height.
EMAIL_URLBase url used inside the email's links.

The stored content above renders through Mustache the same way, so a stored message can carry its own {{placeholders}} before it is dropped into this outer template.

Contact forms & captcha

For a public contact form, validate the reCAPTCHA on the incoming Request before sending — it checks the g-recaptcha-response field against EMAIL_RECAPTCHA_SECRET:

use Framework\Email\Email;

if (Email::isCaptchaValid($request)) {
    Email::send(/* … */);
}
